# Lab 204 Digital Twin — project notes for Claude / new sessions

Standalone Three.js (r128, classic scripts, **no build step**) app served by the Lab Manager FastAPI backend at `/twin/`.
Deployment repo: `aizyaguev-bot/DCIM-204`, folder `lab-twin/`. Additional private copy: `A7asaf-cloud/DCIM-204-Lab-Manager`. Production: VM `yokbvdiprd955`, `~/DCIM-204`, uvicorn on :8000 (venv: `backend/.venv`).

## Files
- `index.html` — layout: header (search, Edit, Screen, Backend), stats bar, left sidebar (filters/legend/tree), 3D viewport (toolbar, rack bar, zoom buttons, save bar, move banner), right detail/editor panel, modals.
- `styles.css` — Lab Manager theme (NVIDIA green `#76b900` on zinc, JetBrains Mono). Sections: header, buttons, layout, detail, edit-mode (`.btn-lg`, `.chip-lg`), kiosk (`body.kiosk`), embed (`body.embed`).
- `app.js` — everything: scene/geometry (`buildRoom`, `buildRack`, `buildTrayRack`, `buildCabinet`, `buildItems`), effective model (`computeModel` = JSON + live DCIM), filters/search/tree, detail panel (`renderDetail`), touch editor (`renderEditor`, `startMove/finishMove`), live backend (`connect`, `refreshStatuses`, `outletAction`, `openKvm`), views/camera (`VIEWS`, `flyTo`, `zoomBy`), persistence (`markDirty`, `saveToServer` → `PUT /api/twin-data`, `downloadJson`).
- `lab-data.json` — **the inventory** (room, templates, structure, zones, setups=racks, shelves, storage, items, dcim seed). Edit this, never hard-code inventory in JS.
- `map-controls.js` — `THREE.LabMapControls`, the twin's one camera controller (map-style navigation, see Conventions).
- `vendor/` — three.min.js + OrbitControls.js (local, lab has no internet; OrbitControls is kept but no longer loaded). `photos/` — 4 source photos.
- `floorplan.svg` — 2D plan generated from the JSON (generator scripts live in the Cowork outputs of the original session; regenerate manually if positions change).

## Conventions
- Units: metres. Data axes: `x` across the room (0 = LEFT wall when standing at the entrance), `z` depth from the entrance wall, `y` up. The Three.js world is mirrored on x (`world.scale.x = -1`) so data-x grows to the viewer's right — use `WX()` for camera positions, `transformDirection(matrixWorld)` for directions.
- Rack local frame: front = +x local, width along z, `rot` = yaw degrees (0 → front faces +x, 90 → faces −z, 180 → faces −x).
- IDs: `Z01`, `SETUP-001`, `SHELF-01…28` (4 per rack, L1 = lowest), `STORAGE-01`, `ITEM-0001`. `LIVE-*` = objects that come from the DCIM backend only (not in JSON).
- Floor model (mirrors `frontend/src/components/racks/floors.js`, `shelvesFor` / `floorsFor` / `isStorageRack`): every rack has 4 floors (floor 1 = top); `Storage-Main` and storage-type racks (the rack's first PDU / rack device has model "Storage", like DcimView rackStats) have 16 evenly spaced shelves. lab-data.json keeps the physical shelves it knows; missing floors are derived at build time and never written back (`derived: true`, stable ids `SHELF-<setup>-L<level>` for a rack, `SHELF-<setup>-S<n>` for storage). With top-down numbering the missing floors go below the known shelves, so known floors keep their numbers: Rack-05 has 3 shelves in the JSON and gets floor 4 at 0.8 m (OPT54, u 4, has its mesh and card). When live data changes a rack's floor model, `computeModel()` rebuilds the racks first (`rebuildStatic`). A derived shelf is read-only in Edit layout ("This shelf comes from the DCIM floor model; edit it in Racks": no status / notes / Save), and an editor Save that has no lab-data.json record to write never reports "Saved". Equipment on a shelf is kept below the next shelf (`srec.gap`).
- Status colours: active green, building amber, inactive grey, dismantled rose, unknown dark grey — shown on edge outlines, LEDs and label dots (bodies use realistic colours from `TYPE_BODY`). Confidence: high solid, medium faded, low dashed.
- Backend endpoints used: `/api/devices/`, `/api/rack-slots`, `/api/switch-assignments`, `/api/opt-owners`, `/api/engineers`, `/api/rack-items`, `/api/chillers`, `/api/rack-overrides`, `/api/pdus/{id}/status`, `POST /api/pdus/{id}/outlets/{n}/power`, `/api/kvms/{id}/status`, `/api/kvms/{id}/autologin?port=N`, `GET/PUT /api/twin-data`, `/api/removed-servers` (servers an Admin removed from the lab: their `hidden` identity keys are left out before the U assignment, like DcimView). No IPs/credentials in this folder — ever.
- Shelf rule (v0.3.x, from the Lab Manager rack view): ONE PC per shelf (`type: opt` = upright mini-tower, left slot) + ONE Lab Manager *rack item* on the right (`equip-switch` = switch under test rendered as an NVIDIA-style 1U switch; `equip-ups`, `equip-other` = generic box). U01 = top shelf. Outlet labels like "empty" / "KVM Power" are filtered by `NON_SERVER_LABEL`. When connected, live rack items are authoritative: JSON `equip-*` with the same name, or on a shelf that has a live rack item, are dropped (no doubles). `switch-assignments` (mgmt switch·port) is only shown as text on the PC.
- Live data is authoritative (WP1, 2026-11): while connected, Lab Manager is the inventory of every DCIM-mapped rack (a setup with `dcimRack`). In `computeModel()` (live branch) a lab-data.json `opt` with no live PDU label, and every JSON `equip-*`, `pdu` or `kvm` record with no live match (`!live.device`), whose setup is mapped gets `setup = null`, `shelf = null`, `notInLm = true` (`jsonPlace` keeps where the file put it): it is listed under Unplaced as "In lab-data.json, not in Lab Manager" (own group in `renderUnplaced`, data-quality entry, `placeLabel`). One server and one unit per floor then hold. lab-data.json still supplies the geometry, chillers / carts / storage and the inventory of unmapped racks; offline (`!live.connected`) nothing changes. Edit layout: a Lab Manager record (`LIVE-*`, `live.inDcim === true` or `movesViaDcim`) gets only Move, Owner and an "Edit details in Racks" link (`#eRacks`, `racksHref(rack)` = `/?tab=racks&rack=<rack>`, `target=_top`; no twin-only copy). `eSave` refuses a name / type / PDU change of such a record. A derived shelf or a shelf of a mapped rack shows "Add in Racks…" (`#eAddRacks`) instead of `#eAddHere`; a mapped rack shows it instead of `#eAddBay` while connected; `#eAddStore` stays. `movePlan` refuses to put a lab-data.json server / unit / PDU / KVM on a mapped rack. `refreshSoon()` runs after `dcimMoveMany()` and `saveDcimOwner()` so the view shows what Lab Manager stored. PDU freshness: `setPduStatus` stores `S.live.pduAt[id]`, a failed status poll `S.live.pduErr[id]`; `pduFresh(id)` = age <= 2.5 × `refresh_seconds` (like the live pill). An old reading keeps the outlet names but its on / off becomes `unknown` in `computeModel` (grey tower, `?`, health "Power reading stale" / "No power reading"), and `powerOf` checks it too; the 1 s ticker (`checkPduFreshness`) rebuilds when a PDU turns stale between polls. The drawer's Power cell says "Stale – last reading hh:mm" or "No data", with "PDU · outlet · age (· last poll failed hh:mm)" under it (`powerSource`); the ping cell is "Ping monitor". A PDU that answers `reachable: false` reads grey "No data · PDU unreachable" (source "… · PDU unreachable · checked N s ago"); the Power cell is red only for Off, grey (`unk`) for Stale / No data / Unknown. A `notInLm` record is reported once in Data quality (its 'unplaced' entry; no aggregated not-in-dcim entry, its live warning stays in the drawer but is not counted), and Edit layout hides Unplace for it (it shows where lab-data.json keeps it). `twin-data.cjs` checks all of this.
- Moving devices: Edit mode → select an object → **Move** → select the destination shelf / rack / storage. Camera drags never move equipment; Edit starts disabled on every load. Each shelf has an invisible `slot` volume (`srec.slot`) shown cyan while moving; `resolveMoveTarget()` maps any hit (item / rack post / slot) to the shelf at that height. OPTs known to the DCIM and `LIVE-` rack items are moved by writing `rack-slots` + `rack-overrides` + `rack-positions` / `rack-items` back to Lab Manager (`dcimMove`), because `computeModel()` derives their shelf from the DCIM U slot (`shelfForU` / `shelfToU`).
- Camera controls (Google Maps style, `map-controls.js`): left drag / one finger pans across the floor (the floor point under the pointer stays under it; near the horizon a bounded scaled pan takes over), right / middle drag or Ctrl·Shift·Alt + left drag rotates (x) and tilts (y) around `controls.target`, the wheel zooms towards the floor point under the pointer, pinch zooms about the fingers' midpoint, a two-finger twist rotates, two fingers pushed up / down together tilt (the choice waits until both fingers have reported a move, or one has moved 24 px while the other holds still, because browsers send one pointermove per finger). The target sits on the floor (y 0): Overview / Top slide it along the line of sight to the floor (`groundedTarget`), and the first gesture after a Focus does the same when the line of sight meets the floor (`controls.groundTarget()`, the view does not change). User rotation keeps the polar angle in [0.02, 1.5] rad and zoom the distance in [min, max]; presets may sit outside and only move back. World Y up, no roll. Short inertia after release, smoothed wheel; `prefers-reduced-motion` turns both off. Arrow keys pan, Shift + arrows rotate / tilt, + / − zoom, N or the compass (top of the zoom bar) turns north up = the wall opposite the entrance at the top (`NORTH` = azimuth π). `orbitTo()` tweens along the sphere. Hover does not move the camera. Canvas clicks select without flying; explicit Focus, Reset and Fit Lab buttons recover the view.
- Navigation that never runs away (WP2, 2026-11): `controls.leftAction` ('pan' | 'rotate') decides what a left drag / one-finger drag does (right / middle drag always rotates; Ctrl·Shift·Alt + left drag does the other action). The Pan / Rotate switch (`#mPan` / `#mRotate`, `aria-pressed`, `setLeftAction`) is stored in localStorage (`twin.leftAction`, via `LS` = try / catch); Move mode uses Pan without storing it (`setLeftAction('pan', false)` in `startMove`) and `cancelMove` restores the stored choice; Rotate is refused while moving. The camera cluster `#navPad` (Pan, Rotate, rotate left / right = `rotateView(±π/12, 0)`, tilt up / down = `rotateView(0, ±0.12)`, like Shift + arrows) has names and titles. Desktop: one column at the right edge, as near the vertical centre as the other overlays allow — `placeNavPad()` (on resize, from `placeAttnDock` / `layoutLegend` / `updateSaveBar` / the environment panel / `renderCrumb`, and the 1 s ticker) keeps it clear of the breadcrumb, save bar, environment panel, move banner, Issues dock, legend and zoom bar; else two columns (`.two`); else just left of an overlay; with no free place it is hidden in Move mode (`.off`) and otherwise covers least. `frameSafe` keeps flights clear of `#navPadBody`. Phones (≤ 720 px, the twin's phone layout; the spec's 640 px would put the desktop column beside the phone zoom column and sheet between 641 and 720 px) keep it behind a 44 px "Rotate" button (`#navMore`, `aria-expanded`) left of the zoom bar's compass; opened, the six buttons sit to its left in three pairs (two rows) level with the zoom bar, so they are on screen wherever the zoom bar is (also 360 × 560 with the half sheet; above the zoom bar, as first built, they went under the header below ~730 px). Escape inside the opened cluster closes it and focuses "Rotate"; phones hide the cluster in Move mode (the banner needs the room); hidden in the rack front. Checked tweens: `zoomBy`, `panBy`, `orbitTo` / `rotateView` and `keepInView` set `S.tween.checked`, and `animate()` runs the collision sweep + `keepRackClearance()` on them and ends the tween where it clamps (`constrainNavigation` returns whether it clamped); a button / key step that a rack stops before half of it is done toasts why ("A rack is in the way: zoom out (−) or pan first", `blockedHint`, at most every 3 s; rotating around a rack's centre in an aisle is often blocked after one step, like the mouse orbit). Quick presses add up: `rotateView` / `zoomBy` / `panBy` continue from where the running step of the same kind (`S.tween.kind` 'turn' / 'zoom' / 'pan') was heading (a turn at most π ahead); a held key's repeats (`e.repeat`) start from the current view, so holding a key keeps one pace. Fit / Focus / view flights and North up (compass, N: a recovery that must reach its heading, `orbitBy(…, 'north', r)`, unchecked) stay unchecked, but North up never ends nearer a rack than allowed: when its end pose at the current distance would, the turn also backs out (larger radius, up to the zoom-out limit). `keepInView(rec)` (canvas clicks only, `select(id, { fromCanvas: true })`, after the drawer opened): translates camera and target together by the box's overflow outside `frameSafe()` (no turn / zoom; a box larger than the area is centred); a target the shift would put under the floor slides back along the line of sight to y 0 (same view — otherwise the target bound lifted camera and target and undid the vertical part, leaving objects under the phone sheet or the legend row), the camera stays above `MIN_EYE` + 5 cm; checked, so it stops where a rack is in the way (it may then not bring the object fully into view); 300 ms, instant with reduced motion. Zoom-out limit: `fitLab` sets `controls.maxDistance = min(MAX_DISTANCE_BASE, 1.6 × overview distance)`; `zoomAbout` never pulls a camera that sits beyond a limit (it may only move back). Hover tip `#hoverTip` (`.hover-tip`): "name · ON / OFF / ? · Rack-03 › Shelf 2" (servers carry the power word; racks show their row; storage its id and name), mouse only with `(any-hover: hover)`; hidden on pointer down, gesture start (`controls` 'start', wheel), camera tweens, pointer leave, Move mode, the rack front and on phones / touch. Hover picks at most every 40 ms and picks the last move of a window when it ends (no stale tip / `S.hover` after a fast move off an object); the tip text is rebuilt when it changes, and the 1 s ticker rewrites a shown tip (`refreshHoverTip`), so a live power change shows while the pointer rests. `twin-nav.cjs` checks all of this (Rack-05 Focus + 20 × `#zIn` and 12 × `#rotL` sampled every frame and the "rack in the way" toast, quick presses adding up / held-key repeats not, North up end clearance, Pan / Rotate drags and Move mode, a click at 90 % of the view and one low in the view (also a phone tap with the sheet opening), the OPT11 tip incl. live change and a fast move off, touch, the cluster clear of every overlay at 1440 / 1024 / 1920 / 1366 × 657 / 1280 × 640 / 844 × 390 / Move at 740 and 800 px, phones 390 × 844 / 375 × 667 / 360 × 640 / 360 × 560).
- Why the old view "ran away" (fixed 2026-11): left drag orbited around a target that was neither under the pointer nor on the floor (room centre at 0.35 × height, or the last focused object), screen-space right-drag pans moved that pivot up / down and deep into the room, the wheel dollied towards the target instead of the pointer, `constrainNavigation` lifted camera and target together whenever the camera dipped under 0.3 m (the pivot crept upward), and releasing a drag dropped the damped remainder of the motion.
- Camera lifecycle: one controller owns navigation; capture/release pointers, cancel on blur, pointer cancel, outside release and resize (`controls.cancel()` stops gesture, inertia and pending zoom). A second finger joins the gesture instead of restarting it. Pointer input cancels camera tweens. The controller emits `change` only for its own movement (never for tweens), so a plain click keeps the view preset. Kiosk mode does not rotate automatically. Target bounds translate camera and target together; a camera under 0.2 m is lifted on its own (never the target); a swept ray prevents zoom/pan crossing equipment surfaces. Rack clearance (`keepRackClearance`, `rackClearance`): user movement (wheel zoom towards the cursor, orbit, pan, inertia — not tweens) keeps the camera at least 0.4 m (`RACK_CLEAR`) outside every rack's box (`localBox`, in the rack's own frame) and every storage unit's box; a step that would end closer keeps only the part that stays clear (camera and target together from where they were, so no jump: the zoom / orbit stops in front of the rack) and drops the remaining inertia / wheel zoom (`controls.halt()`); a camera a preset left closer may move away, never nearer. `twin-shelves.cjs` samples every frame of the verifier's repros (Reset + 5 wheel notches at 35 % / 55 %; Rack-05 Focus + right-drag +200, +250, -700). Labels live in their own stacking context below UI controls.
- Power colours (servers): the OPT tower body and front bezel show the PDU outlet state (`powerOf`): on `#22c55e`, off `#dc2626`, no reading / offline / not in DCIM neutral grey `#6b7280` (never red). Labels add the words ON / OFF / ? (`.pw` tag). Maintenance keeps its health marker (outline, LED, label dot). Health / lifecycle colouring of outlines is unchanged. The legend has its own group for this after Health: tower-shaped swatches "Power ON / Power OFF / Power unknown" (shortened to ON / OFF / ? when narrow, `lg-pshort`), and its tooltip says the body colour is the PDU outlet power, separate from ping health. As the view narrows (`layoutLegend`) the Health title goes first, then the power words shorten, then the health swatches lose their words (tooltips stay), then the power title becomes "Server body"; the power group never loses its words, and when even that does not fit beside the zoom bar the legend moves to a row above it (`lg-above`). (Tried 2026-11: moving the legend above the zoom bar earlier to keep the health words at 1440 with a rack selected / 1024 shrinks the camera framing area — Rack-03 no longer fits, twin-v3.cjs — and shorter words cannot save the ~210 px needed, so health keeps swatches there.) Phones (≤720 px) show only "Server body ▮ON ▮OFF ▮?" above the sheet (hidden in the rack front, which says ON / OFF per server).
- Shelf cards: one per shelf (`renderShelfCards`, `.lbl.shelf-card`, `pointer-events: none`), centred on the shelf front: "Rack-01 › Shelf n", each server as ON/OFF/? · name · host (the ping monitor's host for that server from `GET /api/monitoring`, held in memory only; "no IP" otherwise) and each unit as a kind tag + type (`unitInfo`). The kind is the unit's **stored type**, exactly as the Racks page shows it: SW only for type switch, never guessed in 3D (the site saves type switch when a serial number is entered on a generic unit — `serialUnitType` + `isGenericUnit` in `frontend/src/api/scanParse.js`, used by the unit scan, Scan & Track auto-registration, a scan that fills a generic unit's serial and a serial typed in the DCIM equipment panel — and a type the user picks by hand, such as Other, wins). A switch's model / part_number / name gives its generation (SN#### → Spectrum, QM#### → Quantum); a unit of type other whose model names ConnectX-n / BlueField is tagged NIC / DPU. Deterministic: the same camera and data always give the same cards — no state from earlier frames; card sizes (`full`, `line`, `compact`) are measured off screen once per content and window size (`ensureCardSizes`). Level of detail: full card ≤ 3.4 m, one compact line ≤ 6.5 m (× 1.5 for the selected rack), nothing farther, from behind its rack, or when the sight line from the camera to the card crosses another rack's box (`sightBlocked`: each rack's whole envelope, posts and top cap included, plus 1 cm, so a line grazing a corner post is blocked; the selected rack's own cards stay, faded). The selected rack claims label space first and is never hidden: its full cards, or when they do not all fit on screen its `line` cards (one line with the same detail: power, name, IP / host, unit type), are spread into one column in shelf order (`spreadColumn`); no other rack shows more detail than the selected one. Every other rack (nearest first) shows all-full or all-compact cards: full only when neighbouring full cards fit as anchored (`columnFits`) and none would cover a label already placed; then a compact line that covers a label is hidden, never moved. Cards of other racks drawn over the selected rack's screen outline (`rackFootprint`, convex hull) are hidden when they are farther than it and faded when nearer. Phones show only the selected rack's cards. A server / unit label is skipped while its shelf card is shown. Shelf numbers follow `shelfToU` (1 = top) over the floor model's shelves. `twin-shelves.cjs` checks all of this.
- Same-origin auto-connect; `?embed=1` hides the brand (used by the React tab), `?kiosk=1` = lab screen mode.
- Offline lab: no external requests (fonts come from the local `--mono` / `--sans` stacks). Narrow screens (≤720 px, e.g. the 3D Twin tab on a phone) stack the 3D view above the lists and use one-row edge controls; keep new overlays compact there and leave desktop rules untouched.
- Inventory synchronization: while connected with auto-refresh enabled, reload the same DCIM inventory endpoints every 15 seconds, including rack items, positions, labels, owners, engineers, switch assignments and chillers. Keep the last successful value when an endpoint fails; discard responses from a disconnected/replaced backend session.
- Equipment SN: `serial_number` belongs to the existing rack item, so it follows the device when moved. The live Twin reads it from `/api/rack-items`, displays it in Identity and includes it in search. For photo mapping updates, maintain the corresponding existing `lab-data.json` equipment record as the Git/offline copy and verify the live record after saving. User shelf 1 = top (U01), shelf 4 = bottom (U04); Twin geometric level is the reverse. Do not match devices by name alone.
- Barcode tracking: rack items also carry `barcode`, `shelf_position`, `last_seen_at` and server-managed `tracking_history`. GET `/api/rack-items` returns an ETag; all PUTs must send it as `If-Match` and use the returned saved mapping. Preserve those fields when moving or editing. The React Scan & Track tab and Twin share the same records. A U outside the mapped physical shelf count is unplaced rather than wrapping to another shelf.   See `../docs/barcode-scanning.md`.
- Attention (daily tracking): `computeAttention(model, live, recs)` is pure and returns `[{key, id, setup, severity: crit|warn|info, kind, text, hint}]` sorted by `ATTN_ORDER`. `renderAttention` fills the Attention sidebar tab, the floating collapsible `#attnDock` (top 5; the full list in kiosk mode) and a per-rack 3D badge showing the worst severity. `focusAttention` selects the item or rack, and falls back to the Unplaced tab. Live checks run only while connected; offline mode shows a single "Live data off" entry plus static checks for unplaced items, unmapped racks and low-confidence mapping. Equipment last seen more than `STALE_DAYS` (30) ago is `info:stale`. Both functions are exposed on `window.__twin` for browser tests. Heat is off by default (localStorage). Refreshes must keep panel scroll position and any open editor.

- v3 review fixes (2026-10-25): health caps, the down rack's dashed outline and the selection bars use `linear(hex)` (the renderer writes sRGB, so a raw hex looks pale); the Power… menu names PDU · outlet · state and disables the action that matches the state; the console state is "Unknown" (never "Free") without a loaded, signed-in KVM status; the Issues list has separate connecting / backend-error (Retry now, retry every 15 s) / switched-off cards; 3D labels run an overlap pass every frame (selection and issues are never hidden; the phone labels only issue racks, the selection and search hits); places in the editor and move dialog read "Rack-01 › Shelf 1 (top)" (never SETUP / SHELF ids or L4); the DCIM rack mapping is edited only in Edit layout.

## Dev loop
1. Edit files here. Preview: `start-twin.bat` (Python http.server on :8090) or open `../lab-twin-standalone.html` equivalent by bundling.
2. Sanity: `node --check app.js`.
3. Ship the tested frontend build and backend changes together with the pinned `scripts/install-monitoring.py` installer. It backs up inventory, checks startup and restarts the app safely. See `../docs/navigation-and-owners.md`; avoid ad hoc process termination on the VM.
